# 分档测试设计（S / A / B / C）

## 目标

把「一次调用，模型自己测、自己判」改成**按阶段编排、有计划、有复核**的测试流程。档位决定用多少时间和费用换结论的可信度。

## 决策记录（2026-11-17）

用户要求不缩小范围、一次做完，没有逐条回答设计讨论中的 6 个问题，以下按我的推荐执行，可以再调：

| # | 问题 | 采用 |
|---|---|---|
| 1 | 档位形式 | 档位是预设，底下是一组开关；新建测试时可以选「自定义」改开关 |
| 2 | 红队模型 | 运行时上另一种 harness 可用（已安装且已登录）就用它交叉检验；不可用或执行出错，自动降级为同一 harness 新开会话 |
| 3 | 验收标准以外的发现 | 作为「额外发现」单独列出，带严重程度；**不改变**验收结论，但 critical/high 会在报告和 Linear 评论顶部醒目提示 |
| 4 | 结构化字段 | 仓库新增：安装命令、启动命令、健康检查地址、前端入口地址；测试账号等仍写在测试说明里 |
| 5 | 计划人工确认 | 做成开关，所有档位默认关闭；打开后计划生成即暂停，确认（可附补充说明）后才继续 |
| 6 | 默认档位与预算 | 默认 B；时间上限 C 20 分钟、B 45 分钟、A 90 分钟、S 180 分钟；费用上限默认不限（只有 Claude Code 会报告费用） |

## 档位预设

| 开关 | C 快速 | B 标准 | A 深度 | S 对抗 |
|---|---|---|---|---|
| 测试计划 `plan` | 简版 | ✅ | ✅ | ✅ |
| 托管服务 `service` | — | ✅ | ✅ | ✅ |
| 执行验证 `verify` | 只用命令行、单测、读代码 | ✅ 并自查 | ✅ | ✅ 关键检查跑两遍 |
| UI 走查 `ui` | — | — | targeted：只走验收标准涉及的页面 | full：相关页面全量、控制台、多种宽度 |
| 红队轮数 `red_rounds` | 0 | 0 | 1 | 3（提前收敛就停） |
| 交叉模型 `cross_model` | — | — | ✅ | ✅ |
| 主动探索 `explore` | — | — | — | ✅ |
| 裁决 `judge` | — | — | ✅ | ✅ |
| 时间上限 | 20 分钟 | 45 分钟 | 90 分钟 | 180 分钟 |

## 阶段与流水线

```
plan ─▶ [等待确认] ─▶ service ─▶ verify ─▶ ui ─▶ ( red ─▶ recheck )×N ─▶ explore ─▶ judge ─▶ 收尾
```

- 每个 harness 阶段都是**一次新的会话**（新的 `claude -p` / `codex exec`），只通过平台传入的上下文（计划、证据、质疑）衔接。红队天然是「另一个人」。
- 流水线逻辑是纯函数 `testplan.Next(配置, 输入, 已完成阶段) → 下一步`。后端每收到一个阶段结果就调用一次，决定下一步做什么。可以单测，也不依赖 agent 版本。
- 红蓝循环：第 i 轮红队没有提出质疑 → 收敛，跳出；否则蓝队针对质疑复测，进入下一轮。轮数用完时，最后一轮的质疑交给裁决处理。
- 裁决阶段看到全部材料（计划、蓝队证据、红队质疑、复测回应），逐条给出最终状态（通过 / 未通过 / 无法验证 / **存疑**）和置信度。平台再做一道硬约束：没有证据的「通过」一律降为「无法验证」。

### 失败策略

| 阶段 | 失败时 |
|---|---|
| plan | 记一条说明，verify 改为直接从需求提炼条目 |
| service | 记一条说明；后续阶段被告知「服务启动失败：原因」，可以自己尝试启动 |
| verify | 核心阶段，整个测试判为出错 |
| ui / red / recheck / explore / judge | 跳过并记一条说明，继续往下。红队用交叉模型出错时，先用主 harness 重试一次 |

### 预算

- 时间按「已完成阶段的耗时之和」计算，不算等待人工确认的时间。
- 进入可选阶段（ui、红队轮次、explore）前，如果剩余时间不够这个阶段的最短时长，或已超出费用上限，就跳过，并记「因预算跳过」。
- 每个阶段的超时取「该阶段默认上限」和「剩余预算」中的较小值。

## 托管服务

agent 负责启动和看管被测服务，不交给模型在后台随手起：

1. 启动命令来源：仓库的结构化字段优先，其次用计划阶段模型给出的建议。两边都没有 → 跳过，告诉后续阶段「平台未启动服务」。
2. 先在工作区里同步执行安装命令（有超时），再在**独立进程组**里后台启动服务，输出写入日志文件，并以「🖥」前缀回传到执行流。
3. 轮询健康检查地址，直到返回 2xx/3xx 或超时；没有健康检查地址时，等待几秒后检查进程仍然存活即可。
4. 服务一直运行到测试收尾，各个 harness 阶段共用。收尾或取消时结束整个进程组。
5. 服务进程组 ID 记录在 agent 数据目录里；agent 意外重启后，启动时会把残留的进程组结束掉。

## UI 走查

- 运行时上通过 `npx -y @playwright/mcp@0.0.84 --headless --isolated --output-dir <产物目录> --executable-path <本机浏览器>` 提供浏览器工具。浏览器由 agent 查找（`VERDICT_BROWSER_PATH` → Playwright 缓存里最新的 chromium → 系统浏览器），避免 MCP 要求的浏览器版本与本机不一致时临时下载。Claude Code 用 `--mcp-config … --strict-mcp-config`，Codex 用 `-c mcp_servers.playwright…`。
- 探测项新增「浏览器」：检查 `npx` 是否可用、能否找到浏览器可执行文件。
- 截图保存到 `$VERDICT_ARTIFACTS`（工作区之外的产物目录）。阶段结束后 agent 把新产物通过 HTTP 上传到后端（用运行时令牌认证），报告页显示截图墙。
- 单个文件 10MB 上限，每个测试最多 200 个产物。

## 协议 v2

agent 在 `hello` 里上报 `protocol: 2`。旧版 agent（没有这个字段）不会被派发任务，页面提示「agent 版本过旧，请重新执行安装命令」。

| 方向 | 消息 | 内容 |
|---|---|---|
| 后端 → agent | `start` | 建工作区：`run_id`、仓库、分支 |
| 后端 → agent | `stage` | 执行一个阶段：`stage_id`、`kind`（harness / service）、harness、提示词、Schema、是否挂浏览器、超时；service 阶段带安装命令、启动命令、健康检查地址 |
| 后端 → agent | `finish` | 收尾：停服务、清理 compose、检查源码改动、删工作区 |
| 后端 → agent | `cancel` | 停止当前阶段，然后收尾 |
| agent → 后端 | 事件 `ready` | 工作区就绪，带 commit |
| agent → 后端 | 事件 `stage_started` / `log` / `stage_result` | 日志带 `stage_id` |
| agent → 后端 | 事件 `closed` | 收尾完成：源码改动、diff；出错或取消时带原因 |

**幂等**：后端在任何时候（收到阶段结果、agent 重连、看门狗）都可以调用 `advance(run)`。它要么重发「当前还没有结果的阶段」，要么计算下一步。agent 按 `stage_id` 去重：本地事件日志里已有这个阶段的结果就忽略，正在执行同一阶段也忽略。所以断线、重启、重发都不会导致重复执行。

## 状态

`queued` → `dispatched` → `preparing`（建工作区）→ `running`（执行阶段）⇄ `awaiting_approval` → `finalizing`（收尾）→ `completed` / `error` / `canceled`

## 结论汇总（`testplan.Consolidate`）

以计划条目为准（编号、验收标准、验证方式），依次叠加：verify 的结果 → ui 阶段对 ui 类条目的结果 → 每轮 recheck 的更新 → 红队质疑（挂在对应条目上，标明后来怎么解决的）→ judge 的最终状态和置信度。

总体结论：有任何一条未通过 → 未通过；否则有无法验证或存疑的条目 → 部分无法验证；全部通过 → 通过。额外发现不改变结论。

## 兼容

- 数据库启动时自动迁移，给已有的表补新列，用户现有的数据可以直接升级。
- 旧版测试记录没有阶段数据，报告页按旧格式显示。

## 升级

后端升级后，旧版 agent（协议 v1）连接时会被识别为「版本过旧」，不再派发任务，页面上提示升级。运行时卡片上的「生成升级命令」会重新生成令牌（旧令牌立即失效）和安装命令；在运行时上执行后原地升级，仓库缓存和工作区目录保留。

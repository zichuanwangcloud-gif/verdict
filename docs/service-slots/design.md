# 服务槽位与内存预算

> 目标：解决「并发测试时每个测试都拉起一个被测服务，把服务器内存打爆」。
> 结论：**不跨测试共享被测服务进程**，改为限制同一运行时上同时运行的服务数，并把默认内存预算调保守。

## 1. 结论先行

- **父子单共用一套服务**：只在「同一 commit + 串行执行 + 每轮重置数据」下成立，不是并发共享；收益只是少几次启动，不能降低并发时的内存峰值。
- **多个测试 issue 共用一个服务**：不做。服务进程与代码版本、数据库、生命周期强绑定，共享会破坏隔离，结论不可信、故障不可归因。
- **正确做法**：降低默认并发估算 + 给每台运行时加「服务槽位」上限，必要时把测试拆到多台运行时。

## 2. 现状

每次测试在运行时上是一套完整隔离的环境：

| 资源 | 现状 | 代码 |
|---|---|---|
| 工作区 | 每个 run 一个独立 worktree，锁定到 commit | `internal/agent/workspace.go:135` |
| 端口 | 每个 run 单独分配 | `internal/agent/workspace.go:372` |
| 服务进程 | 每个 run 一个进程组，`service` 阶段启动后常驻到收尾 | `internal/agent/service.go:204`、`internal/agent/session.go:328` |
| 数据库/缓存 | 每个 run 独立 `verdict_*` 库、独立 redis db | `internal/testplan/prompts.go:337` |
| 产物/日志 | `tmp/<runID>/` | `internal/agent/session.go:50` |

并发度默认 `min(CPU/2, 内存/8GB, 8)`（`internal/server/server.go`），每个测试里同时有模型子进程、构建、浏览器和被测服务，8GB 的预算在跑 Web 项目时偏乐观。

## 3. 为什么不能共享服务进程

| 维度 | 共享后的问题 |
|---|---|
| 代码版本 | 服务进程只对应一个 worktree/commit；不同分支/commit 的测试无法共享 |
| 源码改动检测 | harness 与服务在同一目录运行，共享后一个测试的改动会算到另一个测试头上 |
| 数据隔离 | 服务通常在启动时读 DB 配置，换库必须重启；共享进程等于共享库 |
| 生命周期 | 不同档位、不同开始时间需要租约和引用计数；一方收尾会停掉对方的服务 |
| 重试/续跑 | 重启服务前会执行 teardown 删库，会误删对方的数据 |
| 故障归属 | 服务崩了所有测试一起失败，报告无法归因 |
| 进程内状态 | 缓存、后台任务、限流器、全局锁全部共享 |

因此：**数据隔离 ⇒ 每个测试一次服务启动；服务常驻共享 ⇒ 数据不隔离。**

## 4. 设计

### 4.1 默认内存预算

- 每个测试的内存预算从 8GB 调到 **12GB**（`memPerTestMB`）。
- 可用环境变量 `VERDICT_MEM_PER_TEST_MB` 覆盖，适配不同仓库的实际占用。
- 并发度仍取 `min(CPU/2, 内存/预算, 8)`，上限 8。

### 4.2 服务槽位

新增运行时字段 `service_slots`：

| 值 | 含义 |
|---|---|
| `0`（默认） | 按并发度自动：并发度 ≤ 2 时一一对应，否则取一半（至少 2） |
| `1–32` | 手动上限；实际生效值会被并发度截断 |

实际生效值 `effectiveServiceSlots(rt) = max(1, min(用户值或建议值, 并发度))`。

### 4.3 谁占一个槽位

占用者 = **活跃测试中，最新一条 `service` 阶段处于 `pending` / `sent` / `running` / `ok` 的测试**。

- `pending`/`sent`/`running` 先占位：避免多个测试同时看到「有空位」然后一起启动服务。
- `ok`：服务已经常驻，占位直到测试收尾。
- 服务阶段 `error` / `timeout` / `skipped`：不占位。
- 测试进入终态：不再计入。

统计口径见 `internal/server/store/slots.go:CountServiceHolders`。

### 4.4 调度

1. 编排器在**创建 service 阶段之前**检查 `mayStartService`（`internal/server/orchestrator.go`）。
2. 没有空位：不创建阶段，标记 `runs.waiting_slot=1`，直接返回，等槽位释放后再推进。
3. 槽位释放时唤醒等待者：
   - 测试收尾（`onClosed`）
   - 服务阶段失败/超时（`onEvent`）
   - 运行时重连（`onHello`）
   - 看门狗每分钟兜底
   - 页面调高服务槽位后
4. 服务阶段的重试同样受槽位限制；没空位时把重试时间顺延 30 秒。
5. 等待不创建阶段，因此不会消耗阶段时限；但为避免无限排队，从最后一个阶段结束算起超过 **30 分钟**仍无空位时，测试以「等待服务槽位超时」失败，并提示调高槽位或降低并发。

### 4.5 续跑修正

续跑（`CopyStages`）不再复制 `service` 阶段。新测试的 agent 会话是全新的，服务必须重新拉起；复制过来会让流水线误以为服务已在运行，后续阶段连不上服务。顺带修复了复制跳过阶段时 `started_at` 为 NULL 的问题。

## 5. 观测

- 运行时页显示「服务槽位 N（自动/手动）」，可直接点击修改。
- 测试卡片/详情带 `waiting_slot` 字段，可在接口和前端展示「等待服务槽位」。
- 后端日志：`测试 X 等待服务槽位（运行时 #Y）`。

## 6. 不做

- 跨 run 共享被测服务进程。
- 跨运行时自动负载均衡。
- 按实时 RSS 动态调整服务槽位。
- cgroup / 容器级内存硬限制（继续靠并发度和槽位人工控制）。

## 7. 验收

- 单测：`runtimes.service_slots` 迁移与读写、`CountServiceHolders` 口径、`CopyStages` 跳过服务阶段、默认值计算。
- 手工：并发度 4、服务槽位 1，同时提交多个需要服务的测试，观察同一时刻最多 1 个服务进程，其余测试显示等待；调高槽位后等待者自动继续。
- 回归：C 档（不启动服务）不受服务槽位影响，仍按并发度执行。

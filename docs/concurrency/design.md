# 并发执行设计

## 目标

一台运行时现在同一时刻只跑一个测试：调度器看到活跃测试就跳过后面的队列，agent 端也只有单个 session。回归一轮几十个子测试时会排队十几个小时。这个设计让**一台运行时按并发度同时跑多个测试**，同时保证每个测试之间不互相干扰（端口、托管服务、compose 项目、工作区、产物、日志全部隔离）。

## 约束与前提

必须先满足的基础设施，否则并发只会制造随机失败：

1. **端口不能写死**。仓库配置里的启动命令、健康检查地址、前端入口地址常常写死 `3000`，两个测试同时启动会抢端口。平台需要给每个测试注入一个可用端口，命令里用占位符引用。
2. **compose 项目名已经按 runID 隔离**（`COMPOSE_PROJECT_NAME=verdict-<runID>`），这条已经满足。
3. **工作区已经按 runID 隔离**（`runs/<runID>`、`tmp/<runID>`、`artifacts`），这条已经满足。
4. **服务进程组已经按 runID 记 pid 文件**（`pids/<runID>.pgid`），这条已经满足。
5. **费用是真实开销**：N 并发就是 N 倍的模型调用同时打出去。要能按运行时单独设上限，并且回归创建时能看得到预计并发带来的费用。

## 决策记录（2026-11-18）

用户确认「得并发」。以下按我的推荐执行，可以再调：

| # | 问题 | 采用 |
|---|---|---|
| 1 | 并发度定义在哪 | 运行时级，每个运行时一个 `concurrency` 字段（1–32），**用户可以随意设置** |
| 2 | 默认值 | 按机器自动给：CPU 核数的一半、每 8GB 内存一个，取小的，夹在 [1, 8]；用户随时可改成任意值（1–32） |
| 3 | 回归是否单独限流 | 不单独限流；回归子测试和普通测试共用一个队列，但**普通测试优先** |
| 4 | 同仓库是否串行 | 可以并发。同一仓库的工作区是独立 worktree，bare 缓存只在 fetch 时有一把 git 锁，冲突时自动重试一次 |
| 5 | 端口分配 | 平台分配：创建测试时从本次需要的端口开始，向后找 N 个空闲端口（在运行时上探测，见下文）；agent 负责实际占用 |
| 6 | 端口注入方式 | 环境变量 `VERDICT_PORT` / `VERDICT_PORT1` / `VERDICT_PORT2`，仓库配置里用 `${VERDICT_PORT}` 引用；不支持 `$PORT` 这类通用名字，避免和被测应用自己的变量撞车 |
| 7 | 超出并发时 | 排队，和现在一样；日志里记「等待空闲槽位」 |
| 8 | 资源保护 | 运行时上报 `cpu` / `mem_total`；并发调高时页面提示预计内存占用；平台不主动降级，只警告 |

## 端口分配

这是并发里最容易出问题的一环，单独说清楚。

### 需要几个端口

一次测试可能同时占用多个端口：应用本体、数据库、Redis、前端开发服务器。平台不猜，由仓库配置声明：

```
端口需求：2
```

仓库设置里新增「需要的端口数」（0–8，默认 1）。0 表示这个仓库没有端口需求（纯单元测试、纯命令行项目），此时不注入端口变量，也不做探测。

### 谁来分配

平台分配，但**由 agent 真正占用并确认**，因为只有运行时知道本机哪些端口被占：

1. 后端创建测试时先不分配具体端口，只把「需要 N 个端口」写进 `start` 消息。
2. agent 收到 start 后，在本机绑定 `127.0.0.1:0` 拿到 N 个空闲端口（内核保证是空闲的），拿到后**立即关闭**绑定，把这 N 个端口号记进 session。
3. 端口号注入到安装命令和启动命令的环境变量里。
4. 关闭绑定和被测进程真正监听之间有极短的窗口期，理论上可能被别的进程抢走。这个窗口无法完全消除；缓解办法是端口从高位随机区间取（避免 3000 这类常用端口被别的服务撞上），并且**健康检查失败时明确提示「端口可能被占用，重试一次」**。

> 不用「平台从池子里按顺序分配」的原因：后端不知道运行时的端口占用情况，按顺序分配会撞上运行时上已经跑着的其他服务。

### 注入形式

| 环境变量 | 含义 |
|---|---|
| `VERDICT_PORT` | 第 1 个端口，等价于 `VERDICT_PORT1` |
| `VERDICT_PORT1` … `VERDICT_PORT8` | 依次的第 N 个端口 |
| `VERDICT_PORT_COUNT` | 本次分配到的端口数 |

仓库配置里的命令用 `${VERDICT_PORT}` 引用。示例：

```
安装依赖：pnpm install
启动命令：pnpm dev --port ${VERDICT_PORT}
健康检查：http://127.0.0.1:${VERDICT_PORT}/health
前端入口：http://127.0.0.1:${VERDICT_PORT}
```

**兼容性**：没写占位符的命令按原样执行（等于现在的行为）。但并发度 > 1 时，如果仓库声明的端口数是 0 或命令里没有占位符，页面会给一条警告（「这个仓库的启动命令没使用端口占位符，并发时可能互相冲突」），不阻止执行。

### 端口与计划阶段

计划阶段的模型会自己给出一份启动命令建议。给模型的提示词里要求它**用 `${VERDICT_PORT}` 占位符**写端口，并且告诉它本次可用端口数。模型给出的命令里的硬编码端口（比如 3000）会被原样保存，之后并发时冲突风险由上面那条警告提示给用户。

## 调度

### 现在的逻辑

```
阻塞条件：这个运行时名下有任意活跃测试 → 不派
```

### 改成

```
可用槽位 = min(运行时并发度, 运行时实际空闲槽位)
实际空闲槽位由 agent 上报，避免平台认为有时间、agent 其实满了
```

具体做法：

1. **后端**：`Schedule(runtimeID)` 不再判断「有没有活跃测试」，而是统计该运行时名下活跃测试数 `< concurrency` 就循环派到满槽位为止。agent 上报的 `busy` 达到上限时跳过派单；agent 每次补报 probe 都会重新触发一次调度，所以它空闲下来后下一个测试立刻就能派出去，不用等看门狗。
2. **agent**：维护 `sessions map[string]*session`，`len(sessions) < concurrency` 才接受新 start；超了就回 `closed{error:"运行时并发已满"}`，平台把这个测试重新放回排队（**不判失败**，这一点和现在「运行时正忙」直接判错不同）。
3. **普通测试优先**：派单顺序改为「非回归子测试 > 回归子测试」，同一类内按创建时间。现在只是按创建时间，回归会把后面的普通测试堵住。

### agent 上报

`hello` / `probe` 的 `host` 里新增：

```go
type HostInfo struct {
    // …现有字段
    Concurrency int `json:"concurrency"`   // agent 被配置的并发度
    Busy        int `json:"busy"`          // 当前正在执行的会话数
}
```

`busy` 在会话开始和结束时主动补发一次 `probe`，平台据此校准。

`hello.active` 从单个 `string` 改成 `[]string`（协议升到 **v4**）。平台重连后逐个判断：agent 还持有的、平台上已结束的测试，各发一次 cancel。

## agent 多会话

### 改动点

| 现在 | 改成 |
|---|---|
| `ses *session` 单个字段 | `sessions map[string]*session`，按 runID 索引 |
| `current()` 返回当前会话 | `current()` 返回所有会话前的快照；`activeRunIDs()` 返回列表 |
| `onStart`：已有会话就回「运行时正忙」 | 会话数达到并发度才回「并发已满」并**触发平台重新排队** |
| `sessionFor(runID)` | 从 map 里取 |
| 退出时收尾一个会话 | 退出时收尾所有会话 |
| `housekeeping` 的 `GC(active)` 跳过当前会话 | `GC` 接收活跃列表，跳过所有活跃目录 |
| `hello.Active` 单值 | `hello.Active []string` |

### 已经天然隔离、不用改的

- 工作区：`runs/<runID>`
- 临时目录、产物：`tmp/<runID>`、`tmp/<runID>/artifacts`
- 托管服务进程组和 pid 文件：`pids/<runID>.pgid`
- compose 项目：`verdict-<runID>`
- 日志：`logger(runID, stage)`
- 事件日志与续传：全部按 runID 索引

### 一定要处理的共享资源

1. **bare 仓库缓存**：多个会话对同一仓库并发 `git fetch` 会抢锁。处理：fetch 失败且错误里含 `index.lock` / `cannot lock` 时，等待 1–3 秒随机退避后重试一次；再失败则报错。fetch 本身可以改成「先用 `ls-remote` 判断 ref 有没有变，没变就不 fetch」，减少锁竞争。
2. **harness 进程**：Claude Code / Codex 各自是独立子进程，天然可并发。但要确认它们不会写同一个全局配置文件（实测：两者都只读凭据、各自写自己的缓存目录，不冲突）。
3. **浏览器 MCP**：现在是 `--headless --isolated`，每个阶段一个进程，可并发；但要确认 Playwright 的浏览器缓存下载不会在并发时同时触发。
4. **CPU/内存**：并发度建议值按「CPU 核数 / 2」给，而不是核数，因为每个测试里都有模型子进程、构建、浏览器，不是纯 CPU 负载。

## 平台侧

### 数据

| 位置 | 字段 |
|---|---|
| `runtimes` 表 | 新增 `concurrency INTEGER NOT NULL DEFAULT 0`（0 表示跟随按机器算出的建议值） |
| `repos` 表 | 新增 `ports INTEGER NOT NULL DEFAULT 1`（需要的端口数） |
| `runs` 表 | 新增 `ports TEXT NOT NULL DEFAULT '[]'`（agent 实际分配到的端口，用于排查） |

### API

| 方法 | 路径 | 说明 |
|---|---|---|
| PATCH | `/api/runtimes/{id}` | 现有的改名接口扩展为可改 `concurrency`（1–32；0 = 跟随建议值） |
| PUT | `/api/repos/{id}` | 新增 `ports` 字段 |

### 页面

- **运行时**页：显示「并发度 / 当前忙」、CPU 和内存、建议值；可以直接改并发度（1–32），清空则回到建议值。
- **仓库**页：新增「需要的端口数」，并且提示命令里用 `${VERDICT_PORT}`。
- **新建测试**页：如果所选运行时的并发度 > 1 且仓库用了端口占位符，显示「预计并发槽位：N / 当前可用 M」。
- **回归**页：创建时显示「预计总耗时 ≈ 子测试数 ÷ 并发槽位数 × 单档预估时长」。

## 失败的分类与处理

| 情况 | 现在 | 改成 |
|---|---|---|
| agent 已满（收到 start 但没有槽位） | 判测试出错 | **放回排队**，不消耗重试次数；页面显示「等待槽位」 |
| 端口被抢（健康检查超时且端口确实被占） | 启动失败 | 启动失败，提示「端口可能被占用」；自动重试一次（只针对这一种失败） |
| 同一个运行时有测试因为其他测试 OOM 被杀 | 判测试出错 | 判测试出错；页面提示「可能是并发导致内存不足，考虑降低并发度」 |
| 并发度调低时有正在跑的测试 | — | 不中断正在跑的测试，只是不再派新的，直到现有测试结束 |
| 仓库端口数为 0 但并发度 > 1 | — | 允许，但给警告 |

## 观测

- 运行时心跳（`probe`）带 `busy`，平台存最近值并在运行时可视为「忙碌程度」。
- 每次派单和排队都写一条平台日志（不进测试日志），便于排查为什么某个测试一直排着。
- 测试报告里显示本次分配到的端口，便于复现。

## 不做

- **跨运行时的自动负载均衡**：现在是子测试创建时轮转分配 + 空闲时领取，已经够用；不做按实时负载动态迁移。
- **同仓库串行**：明确不做。同一仓库的测试必须允许并发。
- **动态调整并发度**：不做自动升降，只给建议值。
- **端口池持久化**：不做跨测试的端口池，每次重新分配。
- **进程级资源隔离**（cgroup / 容器）：不做，靠并发度建议值人工控制。

## 分阶段实施

| 阶段 | 内容 | 可以单独上线 |
|---|---|---|
| 1 | 端口注入（`VERDICT_PORT`、仓库端口数、提示词） | 是，并发度仍是 1 时也安全 |
| 2 | 运行时并发度配置 + 后端调度按槽位派单 + 普通测试优先 | 是，并发度 = 1 行为和现在一致 |
| 3 | agent 多会话（map、跨会话收尾、GC、bare 缓存锁重试） + 协议 v4 | 是，需要 agent 升级 |
| 4 | 前端展示、回归耗时预估、失败提示 | 是 |

1、2 可以合并成一次发布（对用户无感），3 是一定要 agent 重装的那次。

## 协议变化

- `ProtocolVersion` 从 3 升到 4。
- `hello.active`：`string` → `[]string`。
- `host`：新增 `concurrency`、`busy`。
- `start`：新增 `ports int`（需要几个端口）。端口号不由平台下发，由 agent 分配后写进 `runs.ports`（通过 `ready` 事件回传，新增 `ports []int` 字段）。

## 风险

- **端口窗口期的竞争**：已经用高位随机端口缓解，但仍可能偶发；健康检查失败时的提示和一次自动重试是兜底。
- **内存**：这是并发最实际的限制。一个测试同时有模型进程、构建、浏览器；4 并发的机器至少要有 16GB 可用。建议值保守，页面明确提示。
- **模型侧限流**：并发会同时打模型 API，可能触发供应商侧速率限制。表现为阶段失败，重试逻辑已经存在（执行验证阶段失败会重试一次），但要观察。
- **调试变难**：同时有 N 个测试的输出。日志按 runID 分开，不受影响；但「同一台机器整体在干什么」需要运行时页的忙碌程度来回答。

# 韧性设计：阶段重试、结论强度与手动续跑

## 背景

2026-11-18 的一次 S 档测试（CR-2092）暴露了设计缺陷：

```
plan ok → service ok → verify ok → ui ok
red(codex)      exit status 1（stream disconnected ×5）
red(claude)     exit status 1（API Error: 400 upstream provider rejected）
explore(claude) exit status 1（同上）
judge(claude)   exit status 1（同上）
```

四个阶段全部因模型网关故障失败，蓝队 12 条 AC 全 pass，最终结论却是**通过**。用户看到「通过」会以为经过了红蓝对抗、主动探索和裁决，实际上一步都没跑成。

根因有两层：

1. **可恢复失败被当成跳过**。`docs/tiers/design.md` 写的是「red / explore / judge 失败时跳过并记一条说明」，这个策略对「这个阶段不适用」是对的，对「模型网关抖动」是错的。
2. **结论不反映实际达到的强度**。S 档卖的是对抗 + 探索 + 裁决，缺了这些还叫 S 档结论，是误导。

## 决策记录（2026-11-18）

| # | 问题 | 采用 |
|---|---|---|
| 1 | 裁决缺失时结论 | **降级**：缺裁决的通过不算「通过」，AC 状态降为「存疑」，汇总结论变成「部分无法验证」 |
| 2 | 重试次数 | 写进设置，**默认 5 次**，用户可改 |
| 3 | 手动续跑 | **这一版就做** |
| 4 | 重试与预算 | 重试的耗时计入时间预算；超预算不再重试，直接走降级 |
| 5 | 重试间隔 | 指数退避：30 秒、1、2、4、8 分钟，上限 8 分钟；每次都写进执行流 |

## 一、失败分类

阶段结果增加一个分类字段，由平台根据错误文本判定（不依赖模型的自我描述）：

| 类型 | 判定依据（错误文本匹配，不区分大小写） | 处理 |
|---|---|---|
| `transient` | `stream disconnected`、`upstream provider rejected`、`502`、`503`、`504`、`429`、`rate limit`、`connection reset`、`timeout`、`ECONNRESET`、`overloaded` | 可重试：按退避重试，最多 N 次 |
| `auth` | `401`、`403`、`invalid api key`、`unauthorized`、`not logged in` | 不重试：立刻降级，并提示「检查运行时上 harness 的登录状态」 |
| `other` | 其余失败（harness 崩溃、输出不是合法 JSON 等） | 重试 1 次，仍失败则降级 |

`timeout` 单独区别于其他 `transient`：阶段超时重试时，下一次的超时上限不再放大（防止拖垮预算）。

分类结果写入 `stages` 的 `failure_kind` 列，报告里能看到每个失败阶段属于哪一类。

## 二、重试

### 谁来做

平台（`testplan.Next` 是纯函数，重试属于编排层，放在 `Hub.advance` 里）：

- 阶段结果为 `error` / `timeout` 且分类为 `transient` / `other`，且该阶段的尝试数 < 上限 → **不推进流水线**，而是把阶段状态置为 `retry_wait`，记录 `next_attempt_at`。
- 到点后由看门狗（现在每分钟跑一次）重新推进：创建新的阶段记录（`attempt+1`），提示词里带上一段「上一次这个阶段因为 X 失败，重新执行」。

### 提示词

重试时的提示词在原有内容后追加：

```
## 重试说明
上一次执行这个阶段时失败：<错误摘要>。
这次重新执行，不需要参考上次的任何中间结果。请从头完成本阶段的任务。
```

不把上次的部分输出喂给模型：失败会话的中间结果往往不完整，容易误导。如果模型已经产出部分产物（截图），保留它们，但不作为结论依据。

### 归零与收敛

- 每个阶段的尝试次数独立计算，不跨阶段累计。
- 红队的「交叉模型失败改用主 harness」逻辑保留：交叉模型失败算一次尝试，切主 harness 后还有一次机会；主 harness 也失败则进入重试等待。
- 重试上限用尽 → 该阶段标记为 `failed_degraded`，流水线继续往下（否则一个阶段卡死整个测试），但结论强度会被降级。

## 三、结论强度降级

### 计算

`testplan.Consolidate` 判断每个「承诺阶段」是否成功：

| 角色 | 什么时候算承诺 |
|---|---|
| `verify` | 永远（核心阶段失败直接判出错，不进这里） |
| `ui` | `cfg.UI != none` |
| `red` | `cfg.RedRounds > 0`（任意一轮成功即算达成；全部轮次失败则降级） |
| `explore` | `cfg.Explore` |
| `judge` | `cfg.Judge` |

结果是 `Result.Coverage`：

```go
type Coverage struct {
    Missing []string `json:"missing"` // 未达成的阶段角色
    Degraded bool    `json:"degraded"`
    Reason  string   `json:"reason"`  // 给人看的一句话
}
```

### 对结论的影响

1. **缺裁决**（`judge` 在承诺列表里但没成功）：整份报告的所有 AC 状态从 `pass` 降为 `disputed`，并追加说明「未经裁决」。汇总结论因此变成 `partial`（部分无法验证）。这是最严格的一条，理由是：裁决是 S / A 档结论的最终来源，没有它就不能签字。
2. **缺红队**（`red` 承诺了但全部轮次失败）：结论不变，但在报告和 Linear 评论顶部标注「未经对抗检验」。
3. **缺探索**：结论不变，只做标注。
4. **缺 UI**：结论不变，但 `ui` 类方法的 AC 已经是 `unverifiable`，会自然反映到结论里。

### 展示

测试报告和 Linear 评论顶部：

```
覆盖强度：降级
  未达成：红队质疑、主动探索、裁决（模型网关连续失败，已重试 5 次）
  结论未经裁决，不代表 S 档的验收强度。
```

完整达到时显示「覆盖强度：完整（S 档）」，不占地方。

## 四、手动续跑

### 语义

从一次失败的测试继续，不重新开始：

- 复用原来的计划（如果有），不重新规划；
- 复用原来的服务配置，服务需要重新拉起（上次收尾时已经停掉）；
- 从最后一个成功的阶段之后继续，已成功的阶段不重做；
- 生成一条**新的测试记录**（`parent_run_id` 指向原测试），而不是原地修改。原测试的结果保留，便于对比。

### 前提

- 原测试状态是 `error`（不是 `canceled`、不是 `completed`）；
- 至少有一个阶段已经完成；
- 或者原测试是 `completed` 但结论因强度降级，允许「补跑缺失的阶段」——这种情况同样生成新记录。

### 实现

1. `runs` 新增 `parent_run_id TEXT NOT NULL DEFAULT ''`。
2. `POST /api/runs/{id}/resume`：
   - 校验前提；
   - 复制原测试的 `repo_id / branch / pin_* / issue / config / version_id / regression_id / case_id / plan_source / preset_plan`；
   - 创建新 run，状态 `queued`；
   - **阶段复制**：把原测试里 `status = ok` 的阶段（以及 `skipped` 的）逐条复制到新测试里，作为已完成记录。这样流水线会从「第一个没成功的阶段」继续，而不是从头来。
   - 单次续跑同样受重试上限约束。
3. 前端：测试详情页在 `error` / 降级完成时显示「从失败处继续」按钮；结果页显示「续跑自 #xxxxx」。

### 与回归的关系

回归子测试的续跑走版本页的「重跑未通过」（同一轮追加尝试）。`resume` 只用于普通测试和回归子测试的**手动**续跑，两者不冲突。

## 五、设置

新增两个设置项（页面「设置」）：

| 设置 | 默认 | 说明 |
|---|---|---|
| `stage_retries` | 5 | 单个可重试阶段的最大尝试次数（含第一次），范围 0–20 |
| `stage_retry_delay_seconds` | 60 | 首次重试间隔（秒），之后指数退避，上限 8 分钟；页面按分钟展示 |

存 `settings` 表，键 `stage_retries` / `stage_retry_delay_seconds`。为空或非法时用默认值。

重试用**事件驱动**：安排重试时直接挂一个定时器，到点推进，不必等每分钟一次的看门狗（看门狗仍保留，作为进程重启后的兜底）。

## 六、数据改动

| 表 | 列 | 说明 |
|---|---|---|
| `runs` | `parent_run_id TEXT NOT NULL DEFAULT ''` | 续跑来源 |
| `runs` | `coverage TEXT NOT NULL DEFAULT '{}'` | 覆盖强度（保存后报告可直接读） |
| `stages` | `failure_kind TEXT NOT NULL DEFAULT ''` | `transient` / `auth` / `other` |
| `stages` | `attempt INTEGER NOT NULL DEFAULT 1` | 这个角色的第几次尝试 |
| `stages` | `next_attempt_at TEXT NOT NULL DEFAULT ''` | 退避等待的到期时间 |

`stages` 的 `status` 新增 `retry_wait`。

## 七、协议

**不需要改**：重试、分类、续跑都在平台侧。agent 只是反复收到同一个 `stage` 消息（`stage_id` 不同），已有的去重逻辑不受影响。

## 八、不做

- 把失败会话的部分输出传给下一次尝试（容易误导）。
- 自动续跑（失败了自动从头再来）：费用不可控，只做手动。
- 按错误类型自动切换 harness：保留了现有的交叉模型降级，不做更复杂的路由。

## 九、风险

- **重试把预算吃光**：一次 S 档阶段重试 5 次、每次几分钟，很容易超时。所以重试前先检查剩余预算，不够就不重试、直接降级。
- **网关整体不可用**：重试 5 次也救不回来，只是把失败时间拉长。设置项允许用户调低；平台在连续失败时把提示写清楚（「疑似模型网关不可用，检查运行时的网络和凭据」）。
- **续跑的状态一致性**：复制的阶段记录是快照，原测试如果被判为出错但实际 agent 还在收尾，续跑可能和服务端口冲突。续跑前检查原测试运行时是否仍持有工作区，有就拒绝。
